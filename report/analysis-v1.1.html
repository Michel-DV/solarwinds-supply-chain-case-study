14. Attack-path reconstruction through trust boundaries

The most useful way to model SolarWinds is not as a linear malware chain, but as a sequence of trust-boundary conversions. At each transition, access obtained in one control plane was converted into authority in the next. The malware mattered, but the strategic advantage came from inheriting trust that already existed.

Trust boundaryAttacker leverageDefender assumption placed at risk
Build control planeManipulate what the software factory emits without requiring a visible malicious source-code commit.Reviewed source and a controlled repository are sufficient evidence that the release artifact is trustworthy.
Signing / release planeAllow the modified artifact to move through legitimate signing and vendor distribution.A valid vendor signature implies the upstream build path was uncompromised.
Customer management planeExecute inside an already trusted network-management product with privileged visibility and expected connectivity.Approved infrastructure software deserves broader behavioral exemptions than ordinary processes.
Enterprise identity planeConvert malware-mediated access into valid-account, token, service-principal or federation-based access.Removing the original implant restores the security boundary.
Cloud / data planeUse identity-derived access to reach email, applications and sensitive information with fewer malware-specific signals.Endpoint remediation and IOC blocking are sufficient to end the intrusion.

Where the attack changes character

The decisive transition is the move from artifact-centric access to identity-centric access. Before that point, the defender can still reason primarily about a compromised product, process and network path. After that point, the intrusion can survive as apparently legitimate authentication and administrative activity even if the original Orion component is removed.

Analytical model: build compromise → trusted artifact → privileged execution context → selective victim promotion → identity conversion → durable enterprise/cloud access. The closer the actor moves toward identity, the less useful a malware-only response becomes.

Highest-value defensive choke points

  • Before signing: independently verify provenance between reviewed source, dependencies, build worker and produced artifact.
  • Before deployment: treat privileged management software as a constrained execution environment, not a blanket trust exception.
  • Before identity conversion: isolate management systems from federation, tier-zero administration and unrestricted credential material.
  • After suspected promotion: scope identity and cloud activity immediately instead of waiting for a second malware family to appear.
Michel-DV analysis: the operational center of gravity was not SUNBURST itself. It was the sequence of trust relationships that allowed SUNBURST to become progressively less necessary after access was converted into legitimate-looking identity and administrative paths.

15. Detection hypotheses: where the campaign could surface

These are detection hypotheses, not claims that any single rule would have reliably detected the historical operation. Their purpose is to convert the reconstructed attack path into testable telemetry questions that remain useful against future supply-chain intrusions.

PhaseDetection hypothesisPrimary telemetry
Build manipulationA release artifact differs from what independently rebuilt or provenance-verified inputs should produce, despite no corresponding reviewed source change.CI worker audit, artifact hashes, reproducible-build comparison, build attestations, signing request logs
Trusted executionA privileged management service begins network or process behavior outside its historically narrow operating profile.EDR, parent/child process telemetry, proxy/firewall, application baselines
Victim selectionLow-frequency or structured DNS activity from management hosts correlates with previously unseen external infrastructure.Long-retention DNS, resolver telemetry, passive DNS, asset role context
Promotion / follow-onA trusted server becomes the origin of scripting, remote administration or credential use that is unusual for that system's normal role.EDR, PowerShell/script logging, remote-service logs, authentication telemetry
Identity conversionPrivileged credentials, application identities or token-related operations appear from hosts and sequences that do not match normal administrative workflows.AD authentication, federation logs, IdP audit, service-principal changes, privileged-access telemetry
Cloud persistence / collectionNew application access, mailbox activity or cloud role changes occur shortly after suspicious activity on a high-trust on-premises management system.M365 / cloud audit, mailbox logs, OAuth consent, role and application audit trails

Signal quality improves through correlation

Most individual signals above are weak in isolation. The stronger model is cross-layer correlation: a high-trust management host produces unusual DNS, then launches atypical child activity, followed by privileged authentication or cloud changes. Each event may be explainable alone; the ordered sequence is materially harder to dismiss.

Historical-data requirement: delayed discovery changes the economics of detection. If DNS, identity and cloud audit data expire after a few days, defenders can lose the ability to distinguish broad exposure from selected follow-on compromise when the incident is finally understood.

Detection engineering test

A useful purple-team exercise is to ask whether a trusted management server can generate each class of signal without being automatically suppressed because of its vendor, signature, service account or asset role. High trust should create a narrower behavioral envelope, not a larger blind spot.

16. Red Team research notes: what to emulate safely

The useful Red Team lesson is not to reproduce a real third-party supply-chain compromise. It is to emulate the trust assumptions the operation exploited, inside an explicitly authorized environment, and measure whether defensive controls still work when activity originates from systems defenders already trust.

Research objectiveSafe emulation patternSuccess criterion
Trusted-process blind spotRun benign test actions from an approved lab management-service context or controlled surrogate process.Behavioral controls alert on anomalous activity despite trusted path, signature or asset reputation.
Build integrityIntroduce a controlled difference between reviewed input and lab build output without touching production distribution.Independent provenance or reproducibility checks identify the mismatch before release promotion.
Signing governanceSubmit a deliberately non-compliant artifact to a test signing path using authorized credentials.Policy blocks signing because provenance, requester, build identity or approval chain is incomplete.
Selective promotionGenerate low-noise beacons from multiple lab assets, then activate follow-on simulation only on a designated target.Defenders correlate the weak precursor with later activity instead of treating each signal independently.
Identity follow-throughUse pre-created test identities/tokens to simulate movement from a compromised management tier toward a lab identity or cloud control plane.Tiering, conditional access and identity telemetry detect or prevent the trust transition.

What should not be part of the emulation

  • Compromising or modifying a real vendor, public package, update channel or third-party dependency.
  • Publishing poisoned artifacts outside the authorized laboratory or engagement boundary.
  • Using real production signing keys or federation material when equivalent test credentials can validate the control.
  • Leaving persistent access, altered trust relationships or live credentials behind after the exercise.

Research value

This framing separates capability imitation from security-control validation. A Red Team does not need nation-state access to a software vendor to test the same defensive assumptions: whether trusted infrastructure is over-privileged, whether artifact provenance is independently verified, whether egress from management systems is constrained, and whether identity boundaries stop an initial foothold from becoming durable access.

Final Red Team takeaway: emulate the trust transition, not the geopolitical scale. The strongest exercise is the smallest authorized action that proves whether the same defensive assumption can still be abused.
